# AI-assisted trading and analysis ecosystem

Review date: 2026-10-30. Scope: public documentation, licenses, issue reports and static source inspection. No project was installed or executed, no hosted model was called, and no exchange credentials were used. Current revisions matter: several projects have changed substantially from their older, widely repeated descriptions.

## Decision

**Keep the production trading authority deterministic. Adapt the RD-Agent research loop, and evaluate Vibe-Trading as a gated research pilot (explicit approval, isolated host, no credentials) before writing an equivalent user-facing analysis layer.** Vibe-Trading is the strongest external fit found for the local Claude Code requirement, but its full tool surface includes experimental execution and arbitrary Python. Do not install it alongside trading secrets or accept its backtest output without independent accounting checks.

Runner-up: **Qlib plus the existing local Claude service contract** when the actual experiment requires factor/model datasets and rolling ML evaluation. Qlib provides research infrastructure without requiring an LLM. It is more focused than a multi-market agent workbench, but its stock-oriented examples do not supply crypto funding, collateral or paired execution.

There is no evidence here that adopting any repository supplies a profitable live strategy. Performance claims below are author-reported unless explicitly stated otherwise. Repository maintenance metadata is recorded separately by the ecosystem collector; source pins appear at the end of this report.

## Source-level findings that change the choice

### Vibe-Trading: local Claude compatibility is real, isolation still needs work

At the inspected revision, [`agent/src/providers/claude_cli.py`](https://github.com/HKUDS/Vibe-Trading/blob/78fab6b3f998583f640820db60c155ffa5641a62/agent/src/providers/claude_cli.py) starts the local CLI, requests schema-constrained output, disables native tools/MCP and has the host execute returned tool calls. It strips three Anthropic API/auth/base-URL variables so this path uses the local login. Those are relevant implementation facts, not proof that every installed Claude version accepts the flags or that the account permits the intended schedule.

[`tool_policy.py`](https://github.com/HKUDS/Vibe-Trading/blob/78fab6b3f998583f640820db60c155ffa5641a62/agent/src/providers/tool_policy.py) explicitly documents that its filters are convenience controls rather than a security boundary; the Python-only mode permits `python -c`. Separate OS identity, filesystem restrictions, network policy and absent trading credentials remain necessary. The pinned README (line 296) says five connectors, including Binance and OKX, support "bounded, mandate-gated order placement", labelled "Experimental / use at your own risk". Its capability matrix (lines 492-494) calls the declared broker profiles "declarations, not successful runtime or broker verification". Aggregators calling the whole project read-only are outdated. Use an explicit allowlist of research/data tools, not a broad install with execution connectors available.

A concrete correctness warning is [issue #2088](https://github.com/HKUDS/Vibe-Trading/issues/2088): a user reported spot BTC backtests receiving perpetual funding charges and a commission setting being ignored. A collaborator marked the fix on `main` on October 30 and said it was not yet a new PyPI release. This is responsive maintenance and a reason to pin source, replay the supplied regression, and independently reconcile costs before trusting any report. Neither the issue's P&L table nor the claimed fix was executed by this review.

### RD-Agent: a useful research method, not a turnkey Claude subscription wrapper

The [financial paper](https://arxiv.org/abs/2505.15155) evaluates iterative factor/model development in historical markets. It supports the idea of a hypothesis → code → experiment → feedback loop. It does not demonstrate this user's future crypto returns. The [`LiteLLMAPIBackend`](https://github.com/microsoft/RD-Agent/blob/484776c211e4fbbeef03e0ec00d6bbee7362a4f4/rdagent/oai/backend/litellm.py) calls provider completions and embeddings; swapping only one chat endpoint would not establish compliance with this repo's no-hosted-LLM policy. The [`factor_runner`](https://github.com/microsoft/RD-Agent/blob/484776c211e4fbbeef03e0ec00d6bbee7362a4f4/rdagent/scenarios/qlib/developer/factor_runner.py) executes experiment workspaces. Generated research code must therefore run away from production secrets and its evaluator must be frozen outside the agent's write authority.

Do not let iterative search repeatedly inspect the same “holdout.” Every proposal and failed trial belongs in the registry. Import the discipline before importing an entire Docker-dependent system. Stock benchmark ARR and an advertised small experiment cost are not a crypto profit forecast or a budget guarantee.

### TradingAgents and AI Hedge Fund: analysis quality needs a simpler comparator

TradingAgents' current [`factory.py`](https://github.com/TauricResearch/TradingAgents/blob/c4544913a14ed3df5f1ed7b9e8483270ce20682a/tradingagents/llm_clients/factory.py) routes model requests to provider clients; its [`backtest.py`](https://github.com/TauricResearch/TradingAgents/blob/c4544913a14ed3df5f1ed7b9e8483270ce20682a/tradingagents/backtest.py) is an evaluation entry point. Multi-agent debate is a workflow, not a financial validation method. Pretrained models may know historical events even when supplied data is date-filtered, so future timestamped evaluation is still necessary.

AI Hedge Fund's [`paper/ledger.py`](https://github.com/virattt/ai-hedge-fund/blob/d3a2b6b2bc3579cf0f5bde9cebeea9754f1eae15/hedge_fund/paper/ledger.py) verifies hash links and incorporates halt state; its [`ROADMAP.md`](https://github.com/virattt/ai-hedge-fund/blob/d3a2b6b2bc3579cf0f5bde9cebeea9754f1eae15/ROADMAP.md) distinguishes shipped paper/backtest functions from a planned live broker. Its [`llm/client.py`](https://github.com/virattt/ai-hedge-fund/blob/d3a2b6b2bc3579cf0f5bde9cebeea9754f1eae15/hedge_fund/llm/client.py) uses API clients. Borrow the accountable mandate pattern; do not substitute famous-investor personas for a measured strategy or reimplement an existing tested ledger without a specific gap.

### NOFX: execution capability is not hypothetical

[`auto_trader_loop.go`](https://github.com/NoFxAiOS/nofx/blob/4a5e9ac2a13e6696a276440a3243b2055206512c/trader/auto_trader_loop.go) obtains an AI decision, filters the decision set and calls the execution path. [`auto_trader_risk.go`](https://github.com/NoFxAiOS/nofx/blob/4a5e9ac2a13e6696a276440a3243b2055206512c/trader/auto_trader_risk.go) includes code-enforced position limits. It would be false to say it has no controls. Nevertheless, letting AI select orders in a continuous loop violates the proposed authority separation; deterministic risk checks do not turn model decisions into a validated edge. Frontier's separate approval workflow is worth studying for reviewable trade plans. The root AGPL license and third-party chart terms require a distinct reuse review; copying a UI/source module is not automatically interchangeable with MIT code.

### FinRL-X: actual broker code, different problem

[`trade_executor.py`](https://github.com/AI4Finance-Foundation/FinRL-Trading/blob/4409abe925c904e570be78ebfb5e77ac3491dff8/src/trading/trade_executor.py) turns portfolio weights into Alpaca orders and applies configured order-value/turnover checks on the inspected strategy-execution path. This is stronger evidence of execution functionality than a README screenshot. It is not evidence that every alternative rebalance path shares identical risk semantics, or that it implements spot/perp partial-fill recovery. An adoption review would have to test every submission path, account mode and exception, not merely confirm that a risk method exists.

## Performance evidence: what is stronger and what is still missing

[Awesome-TradingAI's paper](https://arxiv.org/abs/2609.34510) ("Can AI Make Money in Crypto? Measuring the Gap from Backtests to Real Markets", submitted 28 Sep 2026. Its abstract links `github.com/Starlien95/Awesome-TradingAI`. The abstract page was fetched 2026-10-30, sha256 `7404b0b529bd8848…`, copy at `/tmp/crypto-ecosystem/ai-source/arxiv_2609.34510_abs.html`) and repository explicitly distinguish backtests, prospective exchange-paper and live evaluation. The current README says public live runs have delayed publication and keep exact balances, positions and order identifiers private. That is more disciplined reporting than a generic claim of AI outperformance, but we have not reconciled those results to exchange statements or run its code. Different assets, observation windows and method selections prevent a simple leaderboard comparison. It is an evaluation reference, not a reason to deploy its winning model.

Across these candidates, the review found no independently reconciled, sufficiently long, directly transferable live record for this Nigerian-resident BTC/ETH carry proposal. This is a statement about evidence inspected, not proof that no such record exists. AI-generated code, technical analysis, supervised prediction, reinforcement learning, research assistants and autonomous order agents are different products. Their performance cannot be pooled under “AI bot.”

## Architecture variant B: research-first, minimal live surface

1. Keep the existing deterministic market-data, accounting, simulation and risk contracts. Approve no new live authority.
2. Prototype a narrow local Claude research contract. Borrow RD-Agent's explicit hypothesis, executable experiment and feedback structure; the independent evaluator owns data splits and acceptance thresholds.
3. Compare two analysis implementations on the same fixed prompts/data: the minimal local Claude contract and an isolated, restricted Vibe-Trading workbench. Measure factual/source accuracy, deterministic reproduction, unsafe tool rejection, operator time saved and total runtime/cost. Do not judge by length of output or number of agents.
4. Add Qlib only if the winning research question requires model/factor infrastructure. Use an Awesome-TradingAI-style capability manifest and staged evaluation as a cross-check without importing its live credentials or model selection.
5. If strategy research passes, hand a typed, approved proposal to the existing deterministic executor. All external workbenches remain unable to write to the trading account, production database or risk configuration.

This is preferred over installing a combined AI-analysis-and-execution platform now: it reuses what already exists and confines the largest uncertainty to a replaceable research component. The alternative is a richer Vibe-Trading workbench behind the same isolation boundary; adopt that only if the fixed evaluation demonstrates useful savings without weaker evidence or authority controls.
